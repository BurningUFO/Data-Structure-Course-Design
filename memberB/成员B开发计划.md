# 成员 B 开发计划

## 1. 文档目的

本文档面向成员 B，整理当前课程设计中与“查找、排序、推荐、业务交互”相关的任务清单、建议开发顺序和目录草案，作为后续实现、联调和写文档的工作基线。

成员 B 的职责重点：

- 旅游推荐
- 景点/学校查询
- 场所查询
- 美食推荐
- 旅游日记管理、查询与推荐
- AIGC 轻量演示与 Web UI 主入口
- 用户输入输出的业务层组织

---

## 2. 成员 B 目标范围

根据 `课程设计要求.md` 和 `分工初稿.md`，成员 B 负责的核心能力如下：

### 2.1 推荐能力

- 对景点和学校进行推荐
- 支持按热度、评分、兴趣进行排序
- 支持 Top-N 场景，避免全量完全排序
- 适配数据动态变化

### 2.2 查找能力

- 按名称、类别、关键字查找景点、学校、设施和美食
- 支持模糊查询
- 支持日记标题精确查询
- 支持目的地相关日记查询

### 2.3 排序能力

- 按热度排序
- 按评分排序
- 按距离排序
- 按组合权重排序
- 输出前 10 个结果或用户指定的 Top-K 结果

### 2.4 业务交互能力

- 统一用户输入参数格式
- 统一查询结果结构
- 对接成员 A 的距离接口
- 对接成员 C 的数据、全文检索和压缩模块

---

## 3. 任务清单

下面按“必须先做”“中期扩展”“后期联调优化”三个层次整理。

### 3.1 第一优先级：必须先做

这些任务决定成员 B 模块是否能尽快跑起来。

#### 任务 B1：定义统一数据模型

需要先明确成员 B 关心的数据字段，便于和成员 C 对齐数据格式。

建议至少确认以下实体：

- `scenic_spot`
- `school`
- `facility`
- `food_item`
- `restaurant`
- `diary`
- `user_profile`

建议字段：

- 基础字段：`id`、`name`、`category`
- 展示字段：`description`、`tags`、`keywords`
- 排序字段：`heat`、`rating`
- 位置字段：`site_id`、`node_id`
- 扩展字段：`cuisine`、`destination`、`author_id`

交付物：

- 数据字段清单
- 输入样例
- 输出样例

#### 任务 B2：实现基础排序能力

实现后续推荐和查询都要复用的排序能力：

- 按热度排序
- 按评分排序
- 支持多关键字排序
- 支持升序/降序

建议先封装成可复用的通用排序接口，而不是直接写死在某一个功能里。

交付物：

- 通用排序函数
- 排序字段配置规则
- 基础测试样例

#### 任务 B3：实现 Top-N 推荐能力

这是课程要求里的重点之一。

目标：

- 不经过全量完全排序，得到前 10 个结果
- 支持景点/学校推荐
- 后续可复用到美食推荐和日记推荐

可选方案：

- 小顶堆维护 Top-K
- 快速选择 + 局部排序
- 有序数组/平衡结构维护动态 Top-K

建议优先路线：

1. 先实现“小顶堆版 Top-K”
2. 后续再补“快速选择版”用于算法对比

交付物：

- Top-K 核心模块
- 算法说明
- 性能对比记录

#### 任务 B4：实现景点/学校查询

支持：

- 按名称查询
- 按类别查询
- 按关键字查询
- 结果按热度/评分排序

这是最早可以做出演示的主链路之一。

交付物：

- 景点查询接口
- 学校查询接口
- 查询结果排序接口

#### 任务 B5：设计统一业务输出结构

避免每个功能返回格式都不一样，方便后续界面或命令行集成。

建议统一返回结构包含：

- `success`
- `message`
- `total`
- `items`
- `sort_by`
- `filters`

交付物：

- 统一响应结构说明
- 统一错误返回格式

### 3.2 第二优先级：中期扩展

这些任务是成员 B 的主体工作，建议在基础能力稳定后推进。

#### 任务 B6：场所查询

功能要求：

- 输入当前位置或选中的景点/场所
- 查询一定范围内的服务设施
- 支持类别过滤
- 按真实距离排序

依赖：

- 成员 A 提供真实路径距离接口

交付物：

- 场所查询业务层
- 分类过滤逻辑
- 距离排序逻辑

#### 任务 B7：美食推荐

功能要求：

- 按热度、评分、距离排序
- 按菜系过滤
- 支持前 10 推荐

依赖：

- 成员 A 的距离接口
- 成员 C 的餐饮数据

交付物：

- 美食推荐模块
- 菜系过滤逻辑
- Top-N 美食排序

#### 任务 B8：模糊查询

功能要求：

- 支持景点、美食、场所等名称模糊匹配
- 支持关键字模糊匹配

可选方案：

- 子串匹配
- 编辑距离
- 前缀匹配 + 倒排辅助

建议优先路线：

1. 先做子串匹配和关键词匹配
2. 再考虑编辑距离增强

交付物：

- 模糊查询模块
- 匹配规则说明
- 误匹配样例测试

#### 任务 B9：旅游日记基础查询

功能要求：

- 按目的地查询相关日记
- 按标题精确查询
- 结果按热度、评分排序

交付物：

- 日记目的地查询接口
- 日记标题精确查询接口
- 日记排序接口

#### 任务 B10：日记推荐

功能要求：

- 按热度、评分、兴趣推荐日记
- 输出 Top-N 日记结果

交付物：

- 日记推荐模块
- 用户兴趣到标签的匹配逻辑

#### 任务 B11：日记管理入口

功能要求：

- 支持旅游日记创建、编辑、删除和评分。
- 支持文字、图片、视频字段的录入或占位展示。
- 与全文检索、目的地查询、推荐结果共用统一返回结构。

交付物：

- 日记管理业务接口
- 评分接口与展示逻辑
- 日记表单 / 详情页 UI

#### 任务 B12：AIGC 轻量演示入口

功能要求：

- 支持“照片 + 文字描述 -> 动画预览”的轻量可演示闭环。
- 允许采用模板化动画、分镜页或 GIF，不要求复杂模型训练。
- 必须在 Web UI 中可见、可触发、可展示结果。

交付物：

- AIGC 轻量演示业务入口
- 预览结果展示页
- 演示说明

### 3.3 第三优先级：后期联调和优化

这些任务更偏集成效果和验收表现。

#### 任务 B13：对接全文检索结果

成员 C 负责全文检索算法，成员 B 负责：

- 接收全文检索结果
- 做结果排序和展示组织
- 与普通查询接口统一返回格式

#### 任务 B14：异常输入和边界处理

需要覆盖：

- 空输入
- 类别不存在
- 关键字无结果
- 排序字段非法
- Top-K 超范围
- 数据缺字段

#### 任务 B15：算法对比说明

课程设计强调算法分析和对比，成员 B 至少应准备：

- 全量排序 vs Top-K
- 简单查找 vs 模糊查找
- 不同 Top-K 策略的复杂度对比

#### 任务 B16：演示链路整理

建议准备以下可演示业务链路：

1. 查询景点 -> 查看推荐结果
2. 选择地点 -> 查看附近设施
3. 选择地点 -> 查看美食推荐
4. 输入目的地 -> 查看相关日记
5. 输入标题/关键字 -> 查找指定日记

## 4. 建议开发顺序

为了尽快产出可运行结果，同时减少对成员 A 和成员 C 的等待，建议按下面顺序推进。

### 第 1 阶段：先把成员 B 的基础骨架搭起来

优先完成：

1. 定义数据字段和统一输入输出格式
2. 写基础排序接口
3. 写 Top-N 推荐接口
4. 写景点/学校基础查询

这一阶段目标：

- 不依赖复杂 UI
- 用最小样例数据跑通“查询 + 排序 + 推荐”链路

### 第 2 阶段：做成员 B 的主体业务功能

优先完成：

1. 场所查询
2. 美食推荐
3. 模糊查询
4. 日记目的地查询
5. 日记标题精确查询
6. 日记推荐

这一阶段目标：

- 把课程要求里成员 B 对应的功能全部覆盖到
- 统一接口风格，减少后期返工

### 第 3 阶段：对接外部模块

优先完成：

1. 接入成员 A 的距离接口
2. 接入成员 C 的全文检索结果
3. 和成员 C 对齐测试数据

这一阶段目标：

- 让“距离排序”和“全文检索展示”真正可用

### 第 4 阶段：性能、边界和验收优化

优先完成：

1. 补测试
2. 补异常处理
3. 补算法分析
4. 整理演示案例

这一阶段目标：

- 为中期检查、讲解和最终验收做准备

## 8. 成员 B 需要尽快和队友确认的接口

### 8.1 和成员 A 确认

- 距离接口输入是什么：地点 ID、节点 ID 还是坐标
- 距离接口输出是否只返回距离，还是同时返回路径
- 距离策略是否区分步行/骑行/电瓶车
- 场所查询使用哪一种距离策略作为默认值

### 8.2 和成员 C 确认

- 景点、学校、设施、美食、日记的数据字段是否统一
- `tags`、`keywords`、`category` 的格式如何定义
- 日记数据中是否已有热度、评分、目的地字段
- 全文检索返回哪些字段

## 9. 建议的近期执行顺序

如果从现在立刻开始，建议按下面顺序动手：

1. 先和组员确认字段和接口草案
2. 先写排序模块和 Top-K 模块
3. 再写景点/学校查询
4. 再写模糊查询
5. 再写美食和场所查询
6. 最后接日记查询、全文检索展示和联调

这样可以最快做出可展示的结果，同时保证后面扩展不会推翻前面的结构。

## 10. 当前最值得先实现的三个模块

如果要从成员 B 的工作里选出最适合马上落地的三个模块，建议是：

### 第一项：`sorter + topk`

原因：

- 几乎所有推荐功能都会复用
- 容易先写出可测试结果
- 方便后期做算法对比说明

### 第二项：`scenic search + recommend`

原因：

- 最容易形成第一条可演示业务链路
- 对成员 A 和成员 C 的依赖较小

### 第三项：`fuzzy search`

原因：

- 可复用到景点、美食、场所和日记查询
- 能明显体现“查找算法”的课程要求
