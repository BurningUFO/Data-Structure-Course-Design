第11周地图道路展示优化方案对比

目标：在不牺牲主链路稳定性和课程验收确定性的前提下，选择一条最有利于冲刺高分的地图展示升级路径。

背景：当前 Web UI 地图层仍基于 SVG 简图，室外边按节点之间的直线绘制。本规划聚焦“道路看起来是否更像真实校园道路”这一问题。

一、结论先行

如果目标是冲刺极高课程分数，主建议不是直接押注最高难度，而是选 方案 A：geometry 折线道路渲染 作为正式实施方案。它能明显提升视觉可信度，且不会把第 14-15 周的时间窗口变成地图层重构工程。

推荐结论：方案 A 的综合得分最高。方案 B 的天花板更高，但风险集中在底图校准、路网表达、交互回归和时间失控，对课程项目最后两周来说过重。

二、两种方案总览

方案 核心改法 预计工作量 难度 成功概率 对高分价值
方案 A
中高难度		 保留现有 SVG 简图框架；给室外 edge 增加可选 geometry 折线点；边和路线都按折线绘制。 约 4 到 6 人日 中高 约 80% 高。能明显改善观感，且不破坏现有主链路。
方案 B
高难度		 把简图升级成准真实地图层；引入底图或 GeoJSON 式路网渲染、坐标校准、分层地图表现。 约 8 到 14 人日 高 约 50% 最高。展示冲击力最强，但极易挤压测试和验收收口。

三、方案 A：中高难度 geometry 折线方案

  • 数据层：在 outdoor edge 上新增可选 geometry 字段，例如 geometry=[{lat,lng}, ...]，允许两点以上形成折线。
  • 服务层：继续读取 outdoor.json，但 _build_map_edges() 需要把 geometry 一并透传给前端。
  • 前端层：把当前的 SVG <line> 改成 <polyline> 或 <path>；路径高亮尽量沿 edge geometry 拼接。
  • 测试层：补 UI demo 测试，断言 geometry 存在时走折线渲染；同时保留 geometry 缺失时的直线回退。
  • 实施重点：先只做室外图；室内仍保持现有步骤展示和节点高亮，不在第 14-15 周引入室内道路精绘。

推荐改动计划：第 14 周前半先完成数据结构设计和 20-30 条代表性主路 geometry 样例；第 14 周后半扩展到全部室外主干 edge；第 15 周只做视觉收口、路径贴路修正和回归测试。

四、方案 B：高难度准真实地图层方案

  • 数据层：不仅要补 geometry，还要考虑底图或 GeoJSON 式路网表达，最好形成更规范的 outdoor 展示数据契约。
  • 服务层：bootstrap 的 map 数据结构可能需要升级为多图层，例如 base_image、roads、nodes、route_overlay。
  • 前端层：现有 SVG 简图逻辑需要明显扩展，甚至要重写渲染方式，处理底图缩放、拖动、坐标校准、站点切换和图层顺序。
  • 交互层：路线高亮必须准确贴路；否则视觉越真实，误差越显眼，反而降低可信度。
  • 验收层：测试不仅要保功能通，还要保证地图缩放、拖动、路径高亮和多目标展示都不回归。

推荐改动计划：只有在第 13 周前主链路、文档、报告、演示脚本都已经非常稳定时，才应进入此方案。若选此方案，建议拆成两个小版本：先做底图校准和道路层，再做贴路路径和分层表现。

五、风险评估

风险点 主要影响方案 概率 影响 说明
道路 geometry 数据补齐工作量被低估 A / B 高 高 当前 outdoor edge 有 162 条，现有数据没有折线点，最大成本在数据而不是前端代码。
路线高亮与道路折线拼接不稳定 A / B 中 中高 需要把 route.path 节点序列稳定映射到 edge geometry；否则会出现跳线、断线。

第 14-15 周时间被地图层吞掉 B 高 高 如果高难度方案推进不顺，会直接挤压最终报告、彩排、体验修边和高优 bug 修复。

六、推荐实施路径

  • 正式决策：选方案 A 作为第 14-15 周正式实施方案，把“真实道路感”做扎实，而不是把地图层做大做重。
  • 技术预埋：在第 13 周结束前，先把 edge geometry 设计成可选字段；这样方案 A 能落地，方案 B 未来也还能往上叠。
  • 执行顺序：先数据后渲染。优先补 geometry 样例和渲染回退机制，再优化视觉细节；不要先做漂亮底图后补道路数据。
  • 验收标准：老师至少能一眼看到道路不再是机械直线；路径高亮大体贴路；功能、测试、演示链路全部保持稳定。
  • 止损规则：如果第 14 周中段还没把主要主干 edge 画顺，就立刻停止向方案 B 漂移，只收口方案 A。

七、Codex 5.5 xhigh 的推荐用法

最有价值的用法不是“让它凭空做真实地图”，而是让它承担高认知负荷但可验证的工作：

  • 根据现有 node 经纬度和 edge 名称，批量生成 geometry 初稿，再由人工快速校正。
  • 生成 geometry 字段迁移脚本、前端 polyline / path 渲染代码和回退逻辑。
  • 补充 route 几何拼接测试、站点切换回归测试和视觉 QA checklist。
  • 如果尝试方案 B，可先让它做底图校准原型，但最终仍需人工验证每条主路和关键节点位置。

现实判断：Codex 5.5 xhigh 可以明显提高方案 A 的成功率，也能帮助方案 B 做原型验证，但它不能消除方案 B 的坐标校准和时间管理风险。

八、最终建议

推荐选择：方案 A

综合“展示提升幅度 / 风险 / 时间可控性 / 验收稳定性”四个维度，方案 A 的总分最高。

它足以把当前“校园简图 + 直线边”升级成“更接近真实道路的校园导览图”，并且符合第 14-15 周应以体验优化和验收收口为主的节奏。

不建议直接选择：方案 B

它的视觉天花板最高，但风险也最高。对课程项目来说，最糟糕的情况不是“不够炫”，而是最后两周为地图层重构牺牲稳定性和收口质量。

如果最终时间比预期更充裕，可以只从方案 B 中挑一个低风险加分项，例如叠加一张经过校准的淡化底图，而不是全面切换路线。

备注：本规划基于当前仓库实现形态评估。当前地图层仍采用 SVG 简图，室外边通过节点投影后直接连线。若后续 outdoor 数据契约发生变化，应同步修订本规划中的工作量和风险预估。
