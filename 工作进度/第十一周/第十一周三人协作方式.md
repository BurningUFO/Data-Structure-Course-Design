# 第十一周三人协作方式（5月11日 - 5月17日）

> 本文件由 Member A 视角统筹，用来把 README 工作流、第十一周任务要求、`docs/软件开发任务.md`、`docs/项目代码骨架与职责划分.md`、`docs/课程要求覆盖清单.md` 中已经明确的协作规则整理成可执行流程。  
> 本周定位不是继续零散补原型，而是同时完成三件事：**课程硬指标开始收口、Web 正式产品骨架锁定、核心接口第一轮冻结**，为第 13 周正式产品倒计时。

---

## 1. 本周协作总原则

1. 浏览器主入口优先，新增能力默认先考虑如何在 Web 主入口可见。
2. 接口冻结优先，跨模块字段如果要改，先更新 `docs/项目代码骨架与职责划分.md`，再改代码。
3. 数据与课程要求优先，`>=10` 用户样例、200+ 对象方案、课程要求覆盖清单不能继续后移。
4. 第 14-15 周只做体验优化和验收收口，因此第十一周必须把第十三周前的主链路和硬性要求先锁住。

---

## 2. 三人固定职责

| 成员 | 本周固定职责 | 直接产出 |
|------|--------------|----------|
| Member A | 路径接口冻结、多目标路径展示字段、室内/跨层路径错误提示口径、性能验证、答疑材料 | `query_routing` / `query_distance` / `query_multi_target` 第一轮冻结口径，路径样例与验证记录 |
| Member B | Web 主入口、站点切换、统一导航、日记 CRUD、AIGC 入口、多目标路径接入 | 浏览器主骨架、业务入口、页面状态与异常提示 |
| Member C | 课程要求覆盖清单、10+ 用户样例、200+ 数据规模方案、全文检索/压缩/测试/文档底座 | 课程硬指标核验底座、样例数据、测试说明、文档同步 |

## 3. 三条固定协作链路

### 3.1 C → A / B：数据与验收底座先行

- Member C 先把 `>=10` 用户样例、课程覆盖清单、数据规模方案、样例图片/文本、字段说明准备出来。
- Member A 依赖这些数据做 200+ 节点/边规模下的路径性能验证和典型路径样例。
- Member B 依赖这些数据接 Web 页面、日记表单、AIGC 占位结果和课程要求展示口径。

### 3.2 A → B：路径结果按既有契约接入

- Member A 对外继续提供 `query_routing`、`query_distance`、`query_multi_target`。
- Member B 接入时以现有文档契约为准，优先消费已明确的 `path_node_names`、`route_overview`、`path_steps`、`segments`、`total_distance_m`、`estimated_time_s` 等字段。
- 如果前端还缺展示字段，先补文档，再采用追加字段方式扩展，不破坏既有参数顺序和字段语义。

### 3.3 C → B：日记检索、压缩与占位样例接入

- Member C 提供日记全文检索最小字段契约：`diary_id`、`title`、`matched_terms`、`score`、`destination`、`destination_node_id`。
- Member B 负责把这些结果封装到日记中心和统一 UI 输出里，保持 `query_type="diary_fulltext_search"` 及 `results` / `data` 双字段兼容。
- Member C 同时提供媒体占位样例、AIGC 输入描述和压缩/解压验证材料，供 Member B 做页面接入和演示。

## 4. 按时间顺序的执行流程

### 4.1 第一阶段：启动对齐

- 全员开始前先执行 `git pull` 或 `git pull --rebase`，确认本地与远程主线一致。
- 先通读 `工作进度/第十一周/第十一周具体工作任务要求.md`、`docs/软件开发任务.md`、`docs/课程要求覆盖清单.md`。
- Member A 先整理“课程硬指标缺口 + 接口冻结项 + 本周主链路风险”清单，作为三人统一理解版本。
- Member B、C 先对照这份清单确认自己需要的接口、字段、样例和测试入口，避免后面边做边改协议。

### 4.2 第二阶段：先锁课程硬要求和冻结边界

- 围绕课程答疑和第 13 周正式产品倒计时，先把本周不能再拖的硬项锁定：Web 主入口、日记 CRUD、AIGC 轻量演示、10+ 用户样例、200+ 对象方案、课程要求覆盖清单。
- Member A 先确认路径接口哪些字段已经足够前端使用，哪些字段还需要补充。
- Member C 先确认数据字典、课程覆盖表和核验口径，保证 A/B 后续实现用的是同一套定义。
- Member B 在这一阶段不要先拍页面细节，而是先把站点切换、统一导航、主链路入口和错误提示需要的依赖项对齐。

### 4.3 第三阶段：三人并行实现，但公共字段先改文档

- Member A 并行推进单目标、多目标、室内导航展示字段核查，补典型样例和不可达路径提示，并做性能验证。
- Member B 并行推进 Web 首页、站点切换、统一导航、日记 CRUD、AIGC 入口、多目标路径展示接入。
- Member C 并行推进课程覆盖清单、用户样例、数据规模方案、全文检索/压缩验证入口、文档底座同步。
- 这一阶段只要涉及公共字段、统一输出、数据字典或测试命令变更，一律先改文档，再改代码，再通知依赖方。

### 4.4 第四阶段：主链路联调

- 联调顺序固定为：Web 首页与站点切换 → 综合查询/推荐 → 单目标路径 → 多目标路径 → 场所/美食 → 日记中心 → AIGC 占位演示。
- 联调重点不是只看“能跑”，而是检查站点切换后状态是否重置、异常输入是否有提示、不可达路径是否有清晰反馈。
- Member A 重点盯路径返回是否稳定、展示字段是否够用、最短距离/最短时间样例是否都可演示。
- Member B 重点盯浏览器主入口是否已经成为统一骨架，而不是临时演示页。
- Member C 重点盯课程覆盖项、数据规模口径、日记全文检索和压缩链路是否已经能被验收材料引用。

### 4.5 第五阶段：覆盖核验与阻塞修复

- 由 Member C 牵头做课程要求覆盖核验和测试收口，A/B 负责修复阻塞问题。
- 如果 `tests/test_course_requirements.py` 已完成，就按脚本执行并记录结果。
- 如果该脚本尚未完成，就必须给出人工替代校验说明，至少写清楚当前如何核对用户数、数据规模、功能入口、必要文档，以及第十二周如何落成正式核验脚本。

### 4.6 第六阶段：个人陈述与周报收口

- 三人都要在 `工作进度/第十一周/` 下提交 `memberX第11周工作内容陈述.md`。
- 每份陈述至少写清：本周完成事项、涉及文件、测试命令与结果、当前阻塞、下周计划、可演示入口或命令。
- Member A 最后汇总第十一周周报，重点写清“第 13 周正式产品倒计时”下，课程硬指标是否开始收口、Web 主入口是否锁定、接口是否进入第一轮冻结、当前风险是否会影响第十二周全量接入。

## 5. 联调与验收清单

```text
py -3 -B tests/test_graph_load.py
py -3 -B tests/test_routing.py
py -3 -B tests/test_search.py
py -3 -B tests/test_recommend.py
py -3 -B tests/test_diary.py
py -3 -B tests/test_integration.py
py -3 -B tests/test_fulltext.py
py -3 -B tests/test_compress.py
py -3 -B tests/test_ui_demo.py
py -3 -B tests/test_course_requirements.py
```

推荐按下面顺序做验收记录：

1. 浏览器直接进入首页，能看到站点选择、主导航和帮助入口。
2. 查询景点或学校，并从结果进入单目标路径规划。
3. 切到多目标路径，展示访问顺序、总距离、总时间和关键步骤。
4. 进入场所与美食页，确认可以基于真实路径距离排序。
5. 进入日记中心，完成一次创建或编辑，再做全文检索和评分展示。
6. 进入 AIGC 轻量演示入口，展示图片 + 文字描述的占位结果或模板化输出。
7. 切换站点或输入异常参数，确认页面状态会重置，且有明确提示。
