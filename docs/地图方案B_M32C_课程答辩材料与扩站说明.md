# 地图方案 B M32C 课程答辩材料与扩站说明

## 1. 阶段范围

- 阶段：`M32C` 课程答辩材料与扩站说明收口。
- 日期：2026-05-20。
- 站点范围：`PKU` 基线站点 + 20 个扩展校园，共 21 个可用站点。
- 工作边界：只整理文档与展示材料，不新增运行时代码功能，不修改核心架构。
- 禁止事项：未调用 OSMnx、Overpass、web search、外部地图数据下载或新的子 agent / Codex 子进程。

## 2. 一句话答辩结论

地图方案 B 已从单一 `PKU` 校园扩展为“PKU 基线 + 20 所代表性高校”的多校园导览系统，保留课程设计要求中的图结构、最短路径、多目标路线、查询、推荐、全文检索和压缩能力，并通过 `M31D`、`M32A`、`M32B` 三轮回归验证核心 API、UI 演示路径和站点隔离。

## 6. 答辩演示脚本

建议总时长 8-10 分钟：

1. 项目定位（1 分钟）：说明系统解决校园/景区微观导览、查询推荐和室内外一体化路线问题。
2. 架构说明（1 分钟）：展示 `data/sites/<SITE_ID>/` 多校园目录、全局站点注册和 `DemoUIService(site_id)` 站点隔离。
3. 数据结构与算法（2 分钟）：讲分层图、Dijkstra、多目标 DP、Top-K 推荐、倒排索引和哈夫曼压缩。
4. PKU 基线演示（1 分钟）：展示真实地图层、室内楼层、单目标路线和多目标路线。
5. 20 校扩展演示（2 分钟）：切换 `THU`、`WHU`、`HZAU` 等站点，演示地图、查询、推荐和路线均随站点切换。
6. 验收结果（1 分钟）：展示 M31D/M32A/M32B/M32C 文档、测试命令和通过结论。
7. 边界与展望（1 分钟）：说明 20 校扩展为课程演示级模板数据，后续若继续提高真实路网精度，应按离线数据准备流程逐校增强，不在运行时调用 OSMnx 或 Overpass。

## 8. 扩站方法总结

1. 先冻结 `SITE_ID`、学校名称、校区位置和目录结构。
2. 为每校补齐 `outdoor.json`，保证节点、边、分类、路线目标和默认起点可用。
3. 为每校复制室内模板图，保持 `indoor_*.json` 与室外入口节点可连接。
4. 在 `global_sites.json` 注册站点并保持 `sub_graphs` 加载顺序。
5. 校准交通方式、查附近画像、兴趣推荐和演示文案。
6. 用 M31D/M32A/M32B 的回归矩阵验证 API、UI、站点隔离和演示路径。
7. 后续若接入更真实道路或建筑数据，只能通过离线准备脚本和本地 `data/sites/<SITE_ID>/geo/` 文件推进，运行时 UI/API 不直接访问外部地图服务。

## 10. 风险与答疑口径

- 20 个扩展校园当前是课程演示级模板数据，强调站点隔离、流程可复制和核心能力可用；其道路精度不等同于 PKU 的本地 OSM 派生基线。
- 多数扩展校截图中真实线形覆盖率较低属于数据阶段差异，不代表 UI 或路由失败。
- 系统保留 `simple_svg` fallback 和本地 Leaflet 资源，减少演示时外部依赖风险。
- 若答辩老师追问真实地图数据来源，应说明 M7-M9 已把运行时调用和离线数据准备拆开；继续增强必须走本地文件与审计流程，不能在 UI/API 中直接调用 OSMnx 或 Overpass。
