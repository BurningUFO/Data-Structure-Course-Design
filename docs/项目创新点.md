# 项目创新点

> 文档用途：为课程报告和答辩材料提供最终产品口径的创新点说明。
> 原则：只写已经在当前产品中落地或有明确演示入口的能力，避免把早期设想误写成已完成结果。

## 二、创新点一：面向微观场景的真实地图与室内外一体导航

### 痛点

普通地图应用更擅长城市道路导航，在校园、景区、园区内部经常出现三个问题：

- 只显示大路，缺少楼内、步道、门洞和接驳点；
- 路线只到建筑外，不知道如何进入楼层和房间；
- 离线或弱网时地图底图失败，页面可用性下降。

### 实现机制

本项目将早期 SVG 简图升级为 Leaflet + GeoJSON 的真实地图渲染体系，同时保留 SVG fallback。

- `GET /api/map/geojson?site_id=...` 将课程图节点和边转换为 GeoJSON FeatureCollection；
- GeoJSON 坐标顺序采用 RFC 7946 的 `[lng, lat]`；
- `GET /api/map/osm-layers?site_id=...` 加载本地 OSM 派生道路、建筑、水域和绿地图层；
- `GET /api/map/tile/<source>/<z>/<x>/<y>.png` 通过本地代理加载真实瓦片并缓存；
- 前端保留 `renderMap()`、`renderLeafletMap()`、`renderSvgMap()`、`fallbackToSvgMap()` 等稳定入口；
- 室内图通过 `GET /api/map/indoor?...` 获取楼层平面图，支持房间、走廊、墙体、门洞、设施图标和路线高亮；
- `GraphLoader.load_site_graph(site_id)` 把 `outdoor.json` 与 `indoor_*.json` 合并为一张分层图，并用 `gate_link` 连接室外入口和室内入口。

### 代码/API 证据

- `src/ui/demo_service.py`：构造 map capabilities、GeoJSON、OSM 图层、室内地图和路线 UI 数据；
- `src/ui/static/app.js`：Leaflet 渲染、底图切换、路线同步、室内/室外视图切换；
- `src/graph/loader.py`：合并室外、室内和跨层门节点；
- `src/routing/router.py`：按分层路径输出 `segments`、`path_steps` 和跨层摘要；
- `data/sites/PKU/geo/`：本地 OSM 派生道路、建筑、水域和绿地图层。

### 报告可写口径

系统不再只用抽象节点图演示路线，而是把课程图结构和真实地图渲染结合起来：算法层仍以课程图为路由权威，展示层用 Leaflet 和 GeoJSON 呈现节点、道路、路线和室内楼层，从而实现“可计算、可解释、可展示”的微观导览。

### 边界

PKU 的真实地图数据最完整；扩展校园和模板校园主要用于课程演示、站点隔离和流程复用。运行时不直接调用 OSMnx 或 Overpass，真实地图增强应通过离线准备脚本生成本地文件。

## 三、创新点二：200 站点注册与模板复用扩展机制

### 痛点

课程要求景区/校园数量达到较大规模，但逐一采集 200 个真实校园的完整道路、建筑、室内图，在课程周期内成本过高。如果只做一个站点，又无法体现系统扩展能力。

### 实现机制

项目采用“深度核心站点 + 实体扩展校园 + 模板复用站点”的分层扩展策略。

- `data/global_sites.json` 注册 200 个可用站点；
- `PKU` 是深度真实地图核心站点；
- 20 个扩展校园拥有实体 `data/sites/<SITE_ID>/` 目录；
- 其余站点通过 `template_site_id` 指向模板站点；
- `src/site_registry.py` 统一解析展示站点和物理数据站点；
- 模板复用站点用 `display_overrides` 替换节点名、用户名和路线文本；
- `DemoUIService(site_id)` 保证请求、响应、查询、推荐和路线对外仍使用当前站点 ID。

### 代码/API 证据

- `data/global_sites.json`：200 个站点注册；
- `src/site_registry.py`：`resolve_site_data_id()`、`site_uses_template_clone()`、`resolve_site_text_replacements()`；
- `src/ui/demo_service.py`：模板站点禁用真实底图和真实 OSM 上下文图层；
- `tests/test_batch_expand_campus.py`：校验模板站点响应不泄漏模板学校文本；
- `tests/test_m32e_extension_building_minimum.py`：校验扩展校园建筑和模板合同不回退。

### 报告可写口径

系统把“数据深度”和“规模扩展”拆成两条线：PKU 负责证明真实地图和深度导航能力，20 个实体校园负责证明多校园数据目录可复制，200 站点注册与模板复用负责证明系统具备规模化扩展能力。

### 边界

模板复用站点不声明拥有真实道路数据，不加载真实 OSM buildings/water/landuse 图层。其价值在于验证站点隔离、UI 流程、查询推荐和路线接口的可复用性。

## 四、创新点三：动态兴趣画像与可解释个性化推荐

### 痛点

传统推荐常只按热度或评分排序，无法解释为什么推荐某个地点，也不能随着用户行为变化而调整。

### 实现机制

项目实现了静态兴趣 + 动态兴趣画像 + 加权排序的推荐闭环。

- 用户样例在 `data/users.json` 中维护兴趣标签；
- 前端可根据查看推荐、打开详情、地图定位、规划路线、查附近等行为维护动态兴趣画像；
- 后端支持接收 `interest_profile`，并转换为带权兴趣词；
- 推荐排序融合兴趣命中、热度、评分和真实路径距离；
- 推荐结果保留 `interest_match_score`、`recommendation_score`、`interest_reason` 和权重贡献；
- 无明确兴趣时可回退到热度、评分、距离的综合权重排序。

### 代码/API 证据

- `src/recommend/interest.py`：兴趣画像归一化、兴趣命中、权重贡献和推荐得分；
- `src/recommend/ranking.py`：热度、评分、距离的加权排序；
- `src/ui/static/app.js`：动态兴趣画像说明、站点进入推荐弹窗和兴趣推荐交互；
- `POST /api/search/scenic`：综合查询、兴趣推荐、加权排序统一入口；
- `POST /api/diaries/list`：日记推荐也可复用兴趣排序口径。

### 报告可写口径

推荐系统不仅给出 Top-K 结果，还能说明每条结果的推荐原因。系统将用户兴趣、地点类别、标签、关键词、热度、评分和路径距离统一到一个可解释得分中，使推荐从“固定热榜”升级为“可解释的个性化导览建议”。

### 边界

动态兴趣画像当前主要在前端会话和请求参数中体现，属于轻量级产品化实现；没有引入复杂机器学习模型，也不做长期用户画像训练。

## 五、创新点四：弱网环境下的倒排索引检索与哈夫曼压缩

### 痛点

校园和景区中可能存在弱网或断网区域。传统应用一旦无法访问后端搜索服务，日记检索、攻略查找和本地资料浏览都会受影响。

### 实现机制

项目在本地数据上实现全文检索和压缩演示：

- 日记数据保存在本地 JSON 中；
- `DiaryFullTextIndex` 为标题、正文、目的地和标签建立倒排索引；
- 中文检索采用轻量 CJK n-gram，兼容多关键词和同义词；
- 检索结果返回匹配词、相关性分数和正文片段；
- `compress_text()` 使用哈夫曼树生成编码表并打包 bitstream；
- `decompress_text()` 用同一编码表恢复原文；
- `/api/diaries/compress` 对日记文本执行压缩预览并返回 `roundtrip_ok`。

### 代码/API 证据

- `src/compress/fulltext.py`：倒排索引、CJK n-gram、同义词扩展和相关性排序；
- `src/compress/huffman.py`：频率表、哈夫曼树、编码表、bit 打包和解压；
- `src/diary/diary_service.py`：日记全文检索业务封装；
- `POST /api/diaries/fulltext`：全文检索接口；
- `POST /api/diaries/compress`：压缩预览接口。

### 报告可写口径

系统在本地日记数据上构建轻量全文检索和无损压缩能力，体现了倒排索引和哈夫曼树在真实业务场景中的结合：前者解决“如何快速查到内容”，后者解决“如何降低文本存储和传输成本”。

### 边界

当前全文检索不是完整搜索引擎，不支持复杂布尔查询或语义检索；哈夫曼压缩为课程演示级内存结构，重点展示算法正确性、压缩估算和解压回环。

## 六、创新点五：AIGC 轻量预览与稳定回退

### 痛点

课程要求包含基于 AIGC 的旅游动画生成，但真实视频生成成本高、耗时长，并且依赖外部服务。若直接把演示完全押在外部模型上，现场稳定性风险较大。

### 实现机制

项目采用“本地模板预览优先，实时生成可选”的实现策略。

- `data/aigc_media_samples.json` 提供本地样例；
- Web UI 支持选择样例、输入文字描述和风格；
- 默认返回本地 JPG / GIF 和分镜结构，保证无外部 API 时也能看到输出；
- 当配置 `OPENAI_API_KEY` 并选择实时模式时，可调用图片生成接口生成分镜图；
- 实时生成失败或缺少密钥时自动回退到本地模板预览；
- 响应中保留 `generation_mode`、`provider`、`fallback_used`、`fallback_reason` 和 `generation_pipeline`。

### 代码/API 证据

- `src/ui/demo_service.py`：`aigc_preview()`、模板分镜、实时生成和回退逻辑；
- `src/ui/static/app.js`：AIGC 页面交互和预览渲染；
- `src/ui/static/assets/aigc/`：本地可见 GIF 样例；
- `POST /api/aigc/preview`：统一 AIGC 预览接口。

### 报告可写口径

系统将 AIGC 能力设计为可演示、可回退的产品闭环：默认用本地模板保证稳定性，配置外部模型后可升级为实时分镜生成。这种设计兼顾课程验收的可见输出和现场演示的可靠性。

### 边界

AIGC 模块当前不是商用级视频生成系统，重点是证明“图片/文字输入 -> 分镜/动画预览输出”的完整链路，以及外部生成不可用时的稳定降级。

## 七、创新点与课程算法对应关系

| 课程算法/数据结构 | 项目落点 |
|-------------------|----------|
| 图、邻接表 | 多站点室外/室内分层图 |
| Dijkstra | 单目标最短距离、最短时间路线 |
| 状态压缩 DP | 多目标路线访问顺序优化 |
| 堆 | Top-K 推荐、哈夫曼树构建 |
| 排序 | 热度、评分、距离、兴趣综合排序 |
| 哈希/索引 | 站点、用户、节点、日记记录查找 |
| 倒排索引 | 日记全文检索 |
| 哈夫曼树 | 日记文本无损压缩 |

---

## 八、总结

本项目的创新不只停留在算法名称上，而是把课程要求中的数据结构和算法落入可运行产品：地图能显示、路线能高亮、推荐能解释、日记能检索和压缩、AIGC 能输出可见预览，多校园能力也能通过站点隔离和模板复用扩展到 200 站点口径。
