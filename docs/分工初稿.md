# 项目分工与协作建议文档

## 1. 文档目的

本文档用于明确 3 人小组在“基于智能体的个性化旅游系统的设计和开发”中的分工方式、任务边界、协作流程和阶段目标，避免多人同时修改同一部分代码，减少接口混乱和重复劳动。

本方案遵循两个原则：

- 按“算法能力模块”分工，而不是按页面零散分工。
- `main` 分支只保留稳定版本，所有开发先在个人分支完成，再合并到 `main`。

---

## 2. 小组整体协作方案

### 2.1 分支建议

- 成员A分支：`feature/graph-routing`
- 成员B分支：`feature/search-recommend`
- 成员C分支：`feature/integration-docs-data`
- 稳定分支：`main`

### 2.2 总体职责划分

| 成员 | 主要方向 | 核心任务关键词 |
| --- | --- | --- |
| 成员A | 图结构与路径规划 | 建图、最短路径、多点路径、室内外导航 |
| 成员B | 查找、排序、推荐、交互逻辑、UI 产品化与验收演示 | 推荐、模糊查询、Top-N、日记查询、美食推荐、UI展示 |
| 成员C | 数据、测试、系统集成与文档 | 数据准备、全文检索、压缩、测试、材料整理 |

### 2.3 协作基本规则

1. 不直接在 `main` 分支开发。
2. 每人优先维护自己负责的目录和模块。
3. 每次提交只解决一个明确问题，不把无关改动混在一起。
4. 合并前必须说明本次改动影响了哪些模块。
5. 接口一旦确定，不随意修改；如果必须修改，先通知另外两人。
6. 每周至少进行一次集中同步，确认进度、依赖和下周计划。

## 3. 三人详细分工

## 3.1 成员A：图结构与路径规划负责人

### 角色定位

成员A负责本项目最核心的数据结构基础设施，即景区/校园图模型和所有与路线规划相关的算法实现。这部分是整个系统的算法中枢，也是课程设计评分的重点。

### 主要负责内容

#### 一、图模型设计

- 设计景区/校园内部道路图的数据结构。
- 明确节点、边、权重、交通方式、拥挤度等字段。
- 支持室外图和室内图两类结构。
- 定义统一的图数据读取接口，供成员C准备数据后直接导入。

#### 二、路径规划算法

- 实现单目标最短路径算法。
- 实现多目标路径规划算法。
- 支持从当前位置出发，访问多个目标点后返回起点。
- 支持最短距离策略。
- 支持最短时间策略。
- 支持考虑拥挤度后的动态权重。
- 支持交通工具约束下的最短时间路径。
- 预留室内导航路线求解接口。

#### 三、场所查询中的真实距离计算

- 为“附近设施查询”提供真实路径距离，而不是直线距离。
- 向成员B提供距离计算接口，用于场所和美食排序。

#### 四、算法分析与说明

- 整理最短路径、多点路径相关算法说明。
- 对比不同算法方案，例如 Dijkstra、Floyd、A*、状态压缩等。
- 给出时间复杂度、空间复杂度和适用场景分析。

### 建议负责的具体交付物

- 图节点与边的数据结构定义
- 图数据导入模块
- 最短路径模块
- 多目标路径规划模块
- 距离计算接口
- 路径结果输出格式说明
- 路径规划测试样例
- 路径规划模块设计文档

### 与其他成员的接口关系

- 从成员C获取地图、建筑、设施、道路等结构化数据。
- 向成员B提供统一的路径规划和距离查询接口。
- 配合成员C完成算法测试数据和结果记录。

### 阶段任务建议

#### 第1阶段：基础设计

- 确定图模型字段
- 确定输入输出接口
- 完成小规模样例图测试

#### 第2阶段：核心算法实现

- 完成单目标最短路径
- 完成最短时间策略
- 初步支持交通工具约束

#### 第3阶段：扩展与优化

- 完成多目标路径
- 完成室内导航抽象
- 输出算法对比和性能分析

### 不建议负责的内容

- 不负责大规模数据清洗。
- 不负责前端界面细节。
- 不负责周报和最终文档整合。

## 3.2 成员B：查找、排序、推荐与业务交互负责人

### 角色定位

成员B负责所有“用户能直接感受到”的查询、排序、推荐、交互逻辑和 Web UI 产品化，是系统的业务功能中心。课程要求中的旅游推荐、场所查询、日记查询、美食推荐等功能，以及验收所需的核心界面展示和演示入口，应主要由成员B牵头实现。

### 主要负责内容

#### 一、旅游推荐功能

- 实现景点和学校推荐逻辑。
- 根据热度、评价、兴趣完成排序。
- 针对只看前 10 个结果的场景，设计 Top-N 算法。
- 避免对全量数据进行完全排序。

#### 二、场所与美食查询

- 支持按名称、类别、关键字进行查找。
- 支持模糊查询。
- 支持按热度、评价、距离排序。
- 调用成员A提供的距离接口，完成真实路径距离排序。

#### 三、旅游日记管理与交流功能

- 支持按目的地查找相关日记。
- 支持按日记标题精确查询。
- 支持日记创建、编辑、删除、评分和浏览量展示。
- 对接成员C的全文检索结果，完成前端展示或结果组织。
- 实现按热度、评分、兴趣推荐日记。
- 提供 AIGC 轻量演示入口，完成“照片 + 文字 -> 动画预览”的验收级展示。

#### 四、用户交互与系统流程

- 组织用户输入参数的格式。
- 统一查询请求与结果输出结构。
- 配合系统界面或命令行交互，把算法结果转换为用户能看懂的输出。

#### 五、基础 UI 界面与结果展示

- 负责导航、查询、推荐等核心功能的最小可演示界面设计。
- 输出页面线框或静态原型，明确地图区、筛选区、结果区、路径展示区的布局。
- 完成查询结果、推荐结果、路径结果的界面整合，保证验收时可以直接演示。
- UI 以“够用、稳定、便于验收”为原则，优先覆盖主链路，不追求复杂视觉效果。

#### 六、UI 成品化推进（第11-13周）

- 第11周完成产品骨架：统一首页、站点选择器、页面导航、全局状态管理，并把日记管理入口纳入主导航。
- 第12周完成全功能接入：把查询、推荐、路径、多目标、全文检索、压缩、日记 CRUD 和 AIGC 轻量演示统一接到 Web 主入口。
- 第13周完成正式产品冻结：统一视觉、多站点切换、日记中心、媒体占位、响应式布局、帮助页、演示模式、一键预设和运行说明。

#### 七、14-15周体验优化支持

- 第14周只做体验优化：错误与空状态、交互反馈、性能、文案和帮助信息优化。
- 第15周只做验收支持：修高优 bug、配合彩排与现场演示，不再新增课程硬功能。

### 建议负责的具体交付物

- 旅游推荐模块
- Top-N 排序模块
- 模糊查找模块
- 景点/学校查询模块
- 美食推荐模块
- 日记查询模块
- 日记管理（创建 / 编辑 / 删除 / 评分）入口
- 用户输入与结果输出的业务接口
- 导航/查询/推荐界面原型或静态页
- 路径展示与结果面板
- Web UI 首页与站点选择器
- 演示模式与一键启动入口
- 日记中心页面与检索面板
- AIGC 轻量演示预览页
- 业务功能测试样例

### 与其他成员的接口关系

- 从成员C获取景点、设施、美食、日记等基础数据。
- 调用成员A提供的距离和路径接口。
- 向成员C反馈需要补充哪些数据字段和测试样例。

### 阶段任务建议

#### 第1阶段：推荐和查找基础能力

- 完成景点和学校基本查询
- 完成热度、评价排序
- 完成 Top-N 方案验证

#### 第2阶段：扩展业务功能

- 完成场所查询
- 完成美食推荐和模糊检索
- 完成日记基础查询

#### 第3阶段：结果整合与体验优化

- 对接全文检索和压缩功能
- 优化输出格式
- 完成导航、查询、推荐主链路的基础界面
- 补充异常输入和边界情况处理

#### 第4阶段：正式产品冲刺（第11-13周）

- 把最小可演示 UI 升级为正式 Web 主入口。
- 统一站点选择、查询、推荐、路径、日记管理、AIGC 预览的页面状态和切换逻辑。
- 增加验收模式、固定演示链路、帮助页和说明页。
- 第13周结束前冻结界面结构和接口，达到正式产品标准。

#### 第5阶段：用户体验优化与验收支持（第14-15周）

- 根据组内试用和 2026-06-02 答疑反馈优化交互体验。
- 配合成员 C 补用户说明、评价和改进意见、演示稿与答辩材料。
- 只保留小范围修复和文案调整，不再新增课程硬功能。

### 不建议负责的内容

- 不负责底层图结构实现。
- 不负责数据采集主工作。
- 不负责最终总材料汇总。

## 3.3 成员C：数据、测试、系统集成与文档负责人

### 角色定位

成员C负责把项目从“算法模块集合”变成“可验收系统”。这部分工作不只是打杂，而是负责数据质量、测试覆盖、模块联调、过程文档和最终交付材料，直接影响验收效果。

### 主要负责内容

#### 一、基础数据准备

- 构造或采集景区、校园、建筑、服务设施、道路、用户、日记等数据。
- 保证满足课程要求中的硬性数量指标。
- 将原始数据转为程序可读格式，例如 JSON、CSV 或数据库记录。
- 维护数据字典，说明每个字段的含义和用途。

#### 二、文本搜索与压缩算法

- 实现日记内容的全文检索。
- 根据数据规模选择合适的数据结构，例如 Trie、倒排索引或 KMP 相关方案。
- 实现无损压缩与解压功能。
- 输出文本检索和压缩模块的测试结果。

#### 三、系统测试与联调

- 设计单元测试样例。
- 设计集成测试流程。
- 覆盖正常输入、边界输入、异常输入。
- 记录性能测试结果。
- 组织三人模块的联调顺序和联调记录。

#### 四、文档与验收材料整理

- 维护需求、设计、测试、使用说明等文档初稿。
- 汇总每周工作进展，整理周报材料。
- 汇总演示案例、截图、运行步骤和答辩材料。
- 整理系统最终打包结构。

### 建议负责的具体交付物

- 基础数据文件
- 数据字典
- 全文检索模块
- 压缩与解压模块
- 测试用例清单
- 测试记录
- 周报草稿
- 报告和说明文档初稿
- 验收演示材料清单

### 与其他成员的接口关系

- 向成员A提供图数据和建筑设施数据。
- 向成员B提供景点、推荐、美食、日记等业务数据。
- 收集成员A和成员B的模块说明，统一整理到报告中。

### 阶段任务建议

#### 第1阶段：数据和文档底座

- 确定数据字段标准
- 建立第一版数据集
- 建立测试样例框架

#### 第2阶段：算法与联调支持

- 完成全文检索和压缩模块
- 支持成员A、成员B的功能联调
- 开始积累运行截图和测试结果

#### 第3阶段：验收材料收口

- 汇总周报和阶段总结
- 完成最终文档
- 准备演示用数据和演示流程

#### 第4阶段：第11-13周验收底座冲刺

- 第11周补齐 `>=10` 用户样例、缺失字段和课程硬指标缺口追踪。
- 第12周完成数据规模达标、测试补齐和全量功能联调。
- 第13周冻结数据版本、演示样例、截图素材和测试基线。

#### 第5阶段：第14-15周体验与材料优化

- 完成 `用户使用说明`、`评价和改进意见`、`AI 辅助开发能力分析` 等文档定稿。
- 整理报告附件、打包目录、演示录像或截图材料。
- 组织验收前彩排，只修复高优问题。

### 不建议负责的内容

- 不负责主导最短路径算法设计。
- 不负责主导推荐排序算法设计。
- 不应长期代替其他成员写各自模块代码。

## 4. 模块依赖关系

为了减少互相等待，推荐按以下顺序推进：

1. 成员C先准备第一版结构化数据。
2. 成员A基于数据完成图模型和路径接口。
3. 成员B基于数据完成查询、排序、推荐接口。
4. 成员B在第10周起同步推进最小可演示 UI，把查询、推荐、路径规划主链路接到统一界面上。
5. 成员C组织联调，并补测试与文档。
6. 三人一起补边界情况、演示案例和验收材料。
7. 第13周视为正式交付日，14-15周禁止新增课程硬性功能，只允许优化体验与收口材料。

如果数据还没准备完整，也可以先由成员C给出一份最小样例数据，让成员A和成员B先并行开发。

- 本周完成了什么

## 6. 代码协作建议

### 提交建议

- 每次提交只改一个模块或一个问题。
- 提交信息写清楚，例如：
  - `feat: add dijkstra routing`
  - `feat: add top-n scenic recommendation`
  - `test: add diary search cases`
  - `docs: update weekly report notes`

### 合并建议

- 成员先提交到个人分支。
- 合并到 `main` 前，至少让另外一人知道改动范围。
- 如果改了公共接口，必须先同步。
- 不在 `main` 上直接试错。

### 冲突规避建议

- 成员A优先维护图和路径相关文件。
- 成员B优先维护查找、推荐、交互相关文件。
- 成员C优先维护数据、测试和文档相关文件。
- 公共配置文件只由一人负责改，避免频繁冲突。

## 8. 当前最合理的落地顺序

结合课程要求，建议马上按下面顺序开始：

1. 先确定三个人分别是谁，对应成员A、成员B、成员C。
2. 立刻建立 3 个个人分支。
3. 由成员C先产出最小可开发数据集。
4. 由成员A先实现最短路径基础版。
5. 由成员B先实现景点查询和 Top-N 推荐基础版。
6. 第一轮联调只跑通“查景点 -> 看推荐 -> 路线规划”主链路。
7. 第10周先把最小可演示 UI 稳住，确保地图展示、路径展示、查询/推荐结果展示可用。
8. 第11-13周由成员B把该 UI 升级为正式 Web 主入口，补齐多站点、日记中心、AIGC 轻量演示、演示模式和验收脚本。
9. 第14-15周只做体验优化、文档定稿、演示彩排和最终打包。

---

## 9. 结论

三人协作最怕的是职责交叉、接口反复变和所有人都去改同一个入口文件。对这个课设来说，最稳的方案就是：

- 成员A守住图和路径算法。
- 成员B守住查找、排序、推荐和业务流程。
- 成员C守住数据、测试、文档和最后交付。

这样拆分后，既符合课程对算法模块的考查重点，也能让三个人并行推进，后期更容易组织验收和报告材料。
