## 4. 逐项说明

为了让老师和组员更容易理解，下面用更直白的话解释“为什么要这样选”。

### 4.1 为什么景点 / 学校推荐用最小堆做 Top-K

业务特点：

- 用户通常只看前 10 个结果
- 如果景点和学校很多，对全部数据完整排序会浪费时间

因此选择：

- 用最小堆维护当前前 K 个候选项

优点：

- 不需要全量排序
- 数据动态变化时更容易维护前 K 项
- 很适合“推荐前 10 个景点 / 学校 / 美食”的场景

补充说明：

- 为了体现算法对比，后续还可以补一个“快速选择 + 局部排序”的版本

### 4.2 为什么景点 / 学校精确查询用哈希索引

业务特点：

- 用户会按名称查找某个景点或学校
- 查询动作频繁，要求响应快

因此选择：

- 用名称建立哈希索引

优点：

- 平均查询复杂度低
- 插入和更新比较方便
- 适合动态数据场景

如果查询结果不止一个，再做：

- 条件过滤
- 按热度或评分排序

### 4.3 为什么模糊查询单独做成一个能力模块

业务特点：

- 用户输入经常不完整
- 可能只记得一部分景点名、菜系名或关键字

因此选择：

- 用前缀匹配、关键词匹配和结果排序组合实现模糊查询

优点：

- 可以复用到景点、美食、场所和日记等多个功能中
- 比每个功能单独做模糊查找更统一、更易维护

### 4.4 为什么场所查询和美食排序必须依赖真实距离

业务特点：

- 在景区或校园内部，直线距离不等于真实可到达距离
- 可能存在绕路、道路限制、不同交通方式等情况

因此选择：

- 先按类别过滤出候选对象
- 再调用成员 A 的真实路径距离接口
- 最后按真实距离排序

优点：

- 更符合真实导航场景
- 能体现小组分工协作
- 更满足课程对“不能按直线距离”的要求

### 4.5 为什么日记标题精确查询用哈希表

业务特点：

- 课程要求强调“日记数量较大、变化很快时进行高效查找”
- 标题查询属于精确匹配

因此选择：

- 用标题到日记 ID 的哈希映射

优点：

- 平均查询复杂度低
- 适合频繁新增日记的场景
- 结构简单、实现清楚、便于讲解

### 4.6 为什么全文检索和结果展示要分开

业务特点：

- 全文检索算法本身更偏底层文本处理
- 成员 B 更偏业务逻辑组织

因此拆分为：

- 成员 C 负责全文检索算法，例如倒排索引
- 成员 B 负责接收检索结果并统一排序、格式化输出

优点：

- 职责边界清晰
- 联调更容易
- 既符合分工，也能避免多人重复造轮子

## 5. 建议在讲解时重点强调的三点

如果要把这张映射表放进 PPT，建议重点讲下面三句话。

### 第一，推荐功能不是简单排序

因为用户通常只看前 10 个结果，所以我们采用 Top-K 思路，而不是对所有数据完整排序。

### 第二，查询功能不是只做字符串匹配

我们把精确查找、模糊查找、条件过滤和结果排序拆成了可复用的能力模块，既提高效率，也方便扩展。

### 第三，距离相关功能必须依赖真实路径

场所查询和美食推荐中的距离排序，不按直线距离算，而是调用图上的真实路径距离接口，更符合真实旅游场景。
