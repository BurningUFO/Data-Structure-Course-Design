# 成员 B 的架构与逻辑方案

## 1. 文档目的

本文档用于说明成员 B 在“基于智能体的个性化旅游系统”中的职责、模块边界、分层架构和核心业务逻辑。

这份文档的目标有三个：

1. 让组员快速看懂成员 B 负责什么
2. 为第 5 周设计方案讲解提供材料
3. 为后续编码和联调提供统一依据

---

## 2. 成员 B 在项目中的定位

在三人分工中，成员 B 主要负责：

- 查找
- 排序
- 推荐
- 业务交互逻辑

如果把整个系统理解成“用户输入需求，系统给出结果”，那么成员 B 负责的是中间最贴近用户体验的那一层。

简单来说：

- 成员 A 负责“怎么算路”
- 成员 C 负责“数据从哪里来、怎么测、怎么整理文档”
- 成员 B 负责“用户查什么、怎么排、怎么推荐、结果怎么展示得清楚”

因此，成员 B 既不是只写排序算法，也不是只写界面，而是负责把“业务需求”和“算法能力”连接起来。

---

## 3. 成员 B 负责的功能范围

根据课程要求，成员 B 主要覆盖以下功能。

### 3.1 旅游推荐

- 根据热度、评分、兴趣推荐景点和学校
- 支持只输出前 10 个结果
- 尽量避免对全部数据做完整排序

### 3.2 景点 / 学校查询

- 按名称查询
- 按类别查询
- 按关键字查询
- 查询结果支持按热度、评分排序

### 3.3 场所查询

- 在景区或学校内部查找附近设施
- 支持按类别过滤
- 按真实路径距离排序，而不是按直线距离排序

### 3.4 美食推荐

- 按热度、评分、距离推荐美食
- 支持按菜系过滤
- 支持前 10 推荐
- 支持名称、菜系、饭店等内容模糊查询

### 3.5 旅游日记查询与推荐

- 按目的地查找相关日记
- 按日记标题精确查询
- 按热度、评分、兴趣推荐日记
- 对接全文检索结果进行展示和排序

### 3.6 统一业务交互

- 统一输入参数格式
- 统一查询结果结构
- 统一排序、过滤和错误提示方式

---

## 4. 设计目标

成员 B 的模块设计重点不是“功能堆叠”，而是满足下面四个目标。

### 4.1 好理解

模块命名、输入输出、逻辑流程都要清晰，方便组员联调，也方便老师验收时说明。

### 4.2 可复用

排序、Top-K、模糊查找不能每个业务各写一套，而要抽成通用能力。

### 4.3 易扩展

先支持景点、学校、美食、日记等核心对象，后续如果要补更多类型，尽量不推翻已有结构。

### 4.4 易联调

成员 B 的逻辑天然依赖成员 A 的距离接口和成员 C 的数据，因此接口必须统一、稳定、好接入。

---

## 5. 成员 B 的分层架构

为了便于实现和讲解，成员 B 负责的内容可以拆成四层。

## 5.1 表现层

这一层不一定是复杂前端，也可以是命令行、简单页面或接口调用入口。

它负责：

- 接收用户输入
- 展示查询结果
- 展示推荐结果
- 提示错误信息

例如：

- 用户输入“推荐评分最高的前 10 个景点”
- 用户输入“查找图书馆附近的咖啡馆”
- 用户输入“查找标题为西湖一日游的日记”

这一层只负责“收”和“显”，不直接处理核心算法。

## 5.2 业务层

这一层是成员 B 的核心。

它负责：

- 理解用户想查什么
- 决定调用哪种查找逻辑
- 决定按什么规则排序
- 决定是否需要过滤
- 统一返回结果

这一层可以理解为“功能调度中心”。

例如：

- 用户说“推荐前 10 个景点”，业务层就会调用推荐模块和 Top-K 模块
- 用户说“找附近卫生间”，业务层就会调用查询模块，并请求成员 A 的距离接口
- 用户说“按目的地查日记”，业务层就会调用日记查询模块，再按热度和评分组织结果

## 5.3 算法层

这一层负责实现真正的数据结构和算法能力。

成员 B 主要会用到以下算法能力：

- 精确查找
- 条件过滤
- 多关键字排序
- Top-K 排序
- 模糊匹配
- 推荐打分

这一层不直接关心页面怎么显示，而是专注于“给我一批数据，我怎么更高效地找出需要的结果”。

## 5.4 数据层

这一层主要由成员 C 提供基础数据，但成员 B 要明确自己需要哪些字段。

成员 B 主要依赖的数据包括：

- 景点数据
- 学校数据
- 设施数据
- 美食数据
- 日记数据
- 用户兴趣数据

成员 B 不主导数据采集，但必须定义清楚“我要什么数据，才能完成我的业务逻辑”。

## 6. 成员 B 的核心模块划分

为了减少后续代码冲突，建议成员 B 的代码和逻辑按下面方式拆分。

### 6.1 查询模块

职责：

- 按名称查找
- 按类别查找
- 按关键字查找
- 支持基础过滤

应用场景：

- 景点查询
- 学校查询
- 附近设施查询
- 美食查询
- 日记目的地查询

### 6.2 模糊查询模块

职责：

- 支持模糊匹配
- 支持关键词匹配
- 支持名称不完全一致时的查询

应用场景：

- 用户只记得部分景点名
- 用户按菜系、餐厅名或关键词查美食
- 用户按日记主题词查内容

### 6.3 排序模块

职责：

- 按热度排序
- 按评分排序
- 按距离排序
- 支持多条件组合排序

应用场景：

- 景点推荐
- 美食推荐
- 日记推荐
- 场所查询结果排序

### 6.4 Top-K 模块

职责：

- 只取前 K 个结果
- 避免对所有数据做完整排序

应用场景：

- 前 10 景点推荐
- 前 10 学校推荐
- 前 10 美食推荐
- 前 10 日记推荐

### 6.5 推荐模块

职责：

- 将热度、评分、兴趣等信息综合成推荐结果
- 组织输出推荐列表

应用场景：

- 景点推荐
- 学校推荐
- 日记推荐
- 美食推荐

### 6.6 日记业务模块

职责：

- 按目的地查日记
- 按标题精确查日记
- 接收全文检索结果并做结果组织

应用场景：

- 用户浏览旅游日记
- 用户查找指定标题的日记
- 用户根据目的地找经验分享

### 6.7 业务服务模块

职责：

- 统一所有查询和推荐接口
- 调用成员 A 和成员 C 提供的能力
- 返回统一的结果格式

这部分是成员 B 的“门面层”，也是后续最适合接命令行或简单前端的一层。

## 7. 典型业务逻辑流程

为了更容易理解，下面用三个最核心的流程说明成员 B 的逻辑。

### 7.1 旅游推荐流程

用户输入：

- 想看景点还是学校
- 看重热度、评分还是兴趣
- 只看前 10 个结果

系统处理流程：

1. 从数据层读取对应对象集合
2. 根据用户的排序偏好构建比较规则
3. 如果只取前 10，则调用 Top-K 模块
4. 输出推荐结果

输出示例：

- 推荐列表
- 每个对象的名称、类别、热度、评分
- 当前采用的排序依据

### 7.2 场所 / 美食查询流程

用户输入：

- 当前地点
- 想查的类别，比如卫生间、咖啡馆、食堂
- 排序方式，比如距离优先

系统处理流程：

1. 根据类别筛出候选对象
2. 调用成员 A 的距离接口，计算当前地点到候选对象的真实路径距离
3. 按距离、热度或评分排序
4. 输出结果

这里特别强调：

- 不能按地图上的直线距离排序
- 必须按真实可走路径的距离排序

这也是成员 B 与成员 A 联调时最重要的接口之一。

### 7.3 日记查询与推荐流程

用户输入可能有三类：

- 按目的地查日记
- 按标题精确查日记
- 按兴趣看推荐日记

系统处理流程：

1. 先判断用户是哪一种查询意图
2. 调用对应查找模块
3. 如果结果较多，再按热度、评分或兴趣排序
4. 如果是全文内容检索，则接收成员 C 的检索结果
5. 统一组织输出

## 8. 为什么这样设计

这套设计方案的优点主要有以下几点。

### 8.1 把通用能力抽出来，减少重复开发

例如：

- 排序模块可以同时服务景点、美食、日记
- Top-K 模块可以复用在所有前 10 推荐功能里
- 模糊查询模块可以服务多个对象类型

这样既节省开发时间，也方便做算法对比。

### 8.2 业务逻辑和底层算法分开，便于讲解

老师验收时通常既关心“能不能用”，也关心“算法是不是自己实现的”。

把业务层和算法层分开后：

- 业务层负责回答“功能怎么组织”
- 算法层负责回答“为什么这么快、这么合理”

这样更利于答辩和写文档。

### 8.3 方便与组员联调

成员 B 只要把自己的输入输出接口稳定下来，就能和另外两位成员并行推进。

例如：

- 成员 A 只要提供距离接口，成员 B 就能完成距离排序
- 成员 C 只要提供结构化数据，成员 B 就能完成查询和推荐逻辑

这样能减少多人同时改一个文件的冲突。

## 9. 与成员 A、成员 C 的接口关系

## 9.1 成员 B 与成员 A

成员 A 主要提供：

- 最短路径能力
- 真实路径距离计算能力
- 不同交通策略下的时间或距离结果

成员 B 主要调用的接口是：

- 给定起点和目标点，返回真实距离
- 必要时返回路径信息，用于展示

成员 B 会在以下功能中依赖成员 A：

- 场所查询
- 美食推荐中的距离排序
- 未来可能的“路线 + 推荐”联动展示

## 9.2 成员 B 与成员 C

成员 C 主要提供：

- 景点、学校、设施、美食、日记等基础数据
- 全文检索结果
- 测试样例和数据字典

成员 B 主要需要成员 C 保证：

- 数据字段格式统一
- 热度、评分、类别、标签等字段齐全
- 日记数据中有标题、目的地、内容、评分、浏览量等信息

## 11. 结论

成员 B 在整个旅游系统中承担的是“业务交互中心”的角色。

这部分工作的核心不是单独实现某一个算法，而是把查找、排序、推荐这些能力组织成真正可用、可讲解、可联调的业务模块。

本方案的核心思路是：

1. 用分层结构理清职责
2. 用通用模块减少重复开发
3. 用统一接口提高联调效率
4. 先讲清设计，再逐步落地代码
