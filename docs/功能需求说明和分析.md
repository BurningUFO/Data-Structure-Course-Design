## 二、功能一：旅游推荐

### 2.1 功能描述

用户在出行前，系统根据景点热度、用户评价和个人兴趣，向用户推荐旅游目的地（景区与校园）。

### 2.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F1-1 | 按热度对景点/学校排序并推荐 | 必须 |
| F1-2 | 按用户评价对景点/学校排序并推荐 | 必须 |
| F1-3 | 结合用户兴趣标签进行个性化推荐 | 必须 |
| F1-4 | Top-10 推荐，不经过全量完全排序 | 必须 |
| F1-5 | 支持数据动态变化下的推荐更新 | 必须 |
| F1-6 | 按名称、类别、关键字查询景点/学校 | 必须 |
| F1-7 | 查询结果可按热度与评价二次排序 | 必须 |
| F1-8 | 用户可自定义热度/评分/距离各维度权重进行加权推荐 | 创新扩展 |
| F1-9 | 支持错别字容错、拼音首字母、同义词联想的模糊查询 | 创新扩展 |

### 2.3 核心算法与数据结构

- **Top-K 推荐**：使用最小堆（优先队列）维护前 K 条候选，时间复杂度 O(n log K)，避免 O(n log n) 全量排序；可与快速选择算法对比。
- **加权融合排序**：对热度、评分、距离等维度归一化后按用户配置权重线性加权，结果稳定可解释。
- **模糊查询**：Trie 前缀树支持前缀匹配与关键词联想；编辑距离（Levenshtein）支持错别字容错；同义词词典扩展查询覆盖范围。

### 2.4 Q&A

**Q：为什么不直接全量排序取前 10？**  
A：景点数据量大且动态变化，全量排序每次 O(n log n)；堆维护 Top-K 仅需 O(n log K)，K=10 时效率显著更高，且天然支持滑动加载与实时刷新。

**Q：用户兴趣如何获取？**  
A：用户注册时填写兴趣标签（如"历史""自然""美食"），系统将景点 `tags` 字段与用户兴趣标签做交集匹配，匹配度作为兴趣维度得分。

## 三、功能二：旅游路线规划

### 3.1 功能描述

用户进入景区或校园后，系统根据当前位置与目标地点，规划最优游览路线，支持多种路线策略与交通方式，并提供图形化地图展示。

### 3.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F2-1 | 单目标最短距离路线规划 | 必须 |
| F2-2 | 单目标最短时间路线规划（考虑拥挤度） | 必须 |
| F2-3 | 多目标路线规划（访问多点后返回起点） | 必须 |
| F2-4 | 校区内步行/自行车约束下的最短时间路线 | 必须 |
| F2-5 | 景区内步行/电瓶车约束下的最短时间路线 | 必须 |
| F2-6 | 混合交通工具的最短时间路线（多种交通方式组合） | 必须 |
| F2-7 | 室内导航：大门→电梯→楼层→房间 | 必须 |
| F2-8 | 图形化地图展示与路径高亮 | 必须 |
| F2-9 | 时间维度动态边权（拥挤度随时段变化，智能避峰） | 创新扩展 |
| F2-10 | 室内外跨层一体化图结构，多交通工具无缝切换 | 创新扩展 |

### 3.3 核心算法与数据结构

- **图模型**：邻接表表示室外道路图；多层图（Multi-layer Graph）统一表达室内楼层、电梯、室外步道、自行车道、电瓶车路线，节点含 `node_id`、`site_id`、坐标、楼层等属性，边含 `length`、`road_type`、`bike_allowed`、`cart_allowed`、`congestion`、`ideal_speed` 等属性。
- **单目标最短路**：Dijkstra 算法（优先队列实现），时间复杂度 O((V+E) log V)；可与 Floyd-Warshall 在小图上对比。
- **最短时间策略**：边权重新定义为 `length / (congestion × ideal_speed)`，复用 Dijkstra。
- **交通约束**：按 `road_type` 过滤可行边集，构造子图后运行最短路；混合交通工具通过状态扩展（节点状态附加当前交通工具）实现。
- **多目标回路**：状态压缩动态规划（Bitmask DP），精确解适用于目标点数 ≤ 15；目标点较多时可用最近邻启发式 + 2-opt 局部优化近似求解，并在文档中对比两种方案的复杂度与效果。
- **4D 时空动态权值**：将时段（如午间高峰）映射为拥挤度系数，边权随时间变化，路径代价动态更新。

### 3.4 视觉材料说明

地图展示区需呈现：
- 当前园区的节点与边网络（可用示意底图叠加）；
- 规划路径的节点序列高亮；
- 室内楼层切换时的分层视图；
- 路线策略切换面板（距离/时间/交通方式/室内模式）。

### 3.5 Q&A

**Q：室内导航数据难以获取怎么办？**  
A：采用规则生成楼层模板图（标准教学楼：每层若干教室 + 走廊 + 电梯间），明确标注为仿真数据，保证算法可演示。

**Q：多目标路线与单目标有何本质区别？**  
A：单目标为经典最短路问题；多目标（TSP 类）在目标点数增加时搜索空间指数级增长，需要状态压缩 DP 或启发式算法，是课程考查的算法深度重点。

## 四、功能三：场所查询

### 4.1 功能描述

用户在景区或校园内选中某个地点后，系统查找附近一定范围内的服务设施，并按真实路径距离排序展示。

### 4.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F3-1 | 选中地点后查询一定范围内的服务设施 | 必须 |
| F3-2 | 按真实路径距离排序（禁止直线距离） | 必须 |
| F3-3 | 支持按设施类别过滤（洗手间、超市、食堂等） | 必须 |
| F3-4 | 支持输入类别名称查找附近设施 | 必须 |
| F3-5 | 查询结果按距离升序排列 | 必须 |

### 4.3 核心算法与数据结构

- **设施索引**：按 `category` 建立分类索引，支持 O(1) 类别过滤。
- **真实距离计算**：调用成员 A 提供的图上最短路径接口，以路径长度（米）作为排序依据，而非欧氏直线距离。
- **排序**：过滤后对候选设施集合按距离排序，数量通常较小，插入排序或归并排序均可；若候选集较大，可复用 Top-K 堆。

### 4.4 Q&A

**Q：为什么不能用直线距离？**  
A：景区/校园内存在围墙、建筑遮挡、单行道等约束，直线距离与实际步行距离差异显著，会导致推荐结果不准确，影响用户体验。

## 五、功能四：旅游日记管理

### 5.1 功能描述

用户在旅游过程中或结束后，可撰写包含文字、图片、视频的旅游日记，系统统一管理并支持按热度、评分、兴趣推荐。

### 5.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F4-1 | 用户可创建、编辑、删除旅游日记 | 必须 |
| F4-2 | 日记支持文字、图片、视频内容 | 必须 |
| F4-3 | 统一管理所有用户日记 | 必须 |
| F4-4 | 浏览量作为日记热度指标 | 必须 |
| F4-5 | 用户可对日记评分 | 必须 |
| F4-6 | 按热度、评分、个人兴趣推荐日记（Top-K） | 必须 |

### 5.3 核心算法与数据结构

- **日记存储**：JSON 格式，字段包含 `id`、`title`、`destination`、`author_id`、`content`、`heat`（浏览量）、`rating`、`tags`、`created_at`。
- **推荐排序**：复用 Top-K 堆，按 `heat`、`rating` 或加权组合排序；兴趣匹配通过 `tags` 与用户兴趣标签交集计算。

## 六、功能五：旅游日记交流

### 6.1 功能描述

用户可检索、浏览其他用户的旅游日记，支持按目的地、标题、内容全文等多种方式查找，并支持离线检索与压缩存储。

### 6.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F5-1 | 按旅游目的地检索相关日记，结果按热度/评分排序 | 必须 |
| F5-2 | 按日记标题精确查询（支持大规模、高动态数据） | 必须 |
| F5-3 | 日记内容全文检索 | 必须 |
| F5-4 | 日记无损压缩存储与解压 | 必须 |
| F5-5 | 基于 AIGC 的旅游动画生成（照片+文字→动画） | 必须（方案级） |
| F5-6 | 弱网/离线环境下仍可对本地数据进行全文检索 | 创新扩展 |
| F5-7 | 高优离线同步：预先打包高价值日记供断网使用 | 创新扩展 |

### 6.3 核心算法与数据结构

- **标题精确查询**：哈希表，均摊 O(1) 查找，适应高动态（频繁增删）场景。
- **全文检索**：倒排索引（Inverted Index），对日记内容分词后建立词项→文档列表映射；可扩展 TF-IDF 权重提升相关性排序。
- **无损压缩**：哈夫曼树（Huffman Tree），对中文日记文本进行字符级频率统计，生成最优前缀编码，压缩率与解压正确性须可演示。
- **离线全文检索**：在哈夫曼压缩后的本地数据体系上构建倒排索引，断网时仍可对关键词（如"急救""洗手间"）进行高效检索。
- **AIGC 动画**：输入景点照片与文字描述，调用生成式模型输出旅游动画素材；降级方案为模板化幻灯片动画。

### 6.4 Q&A

**Q：倒排索引与哈希表精确查找有何区别？**  
A：哈希表适合精确匹配（标题完全一致），O(1) 查找；倒排索引适合全文检索（内容中包含关键词），支持多词项交集查询与相关性排序，两者互补。

**Q：压缩后还能检索吗？**  
A：倒排索引建立在解压后的词项上，索引本身体积远小于原文，可常驻内存；检索时查索引，按需解压对应文档片段，兼顾存储效率与检索速度。

## 七、功能六：美食推荐

### 7.1 功能描述

用户在选定景区或校园后，系统推荐附近美食，支持按热度、评价、距离排序与菜系过滤，并支持模糊查询。

### 7.2 必须具备的能力清单

| 编号 | 能力描述 | 优先级 |
|------|----------|--------|
| F6-1 | 按热度排序推荐美食（Top-10，不全量排序） | 必须 |
| F6-2 | 按用户评价排序推荐美食 | 必须 |
| F6-3 | 按真实路径距离排序推荐美食 | 必须 |
| F6-4 | 按菜系过滤美食列表 | 必须 |
| F6-5 | 支持名称、菜系、饭店/窗口名称模糊查询 | 必须 |
| F6-6 | 模糊查询结果可按热度、评价、距离多关键字排序 | 必须 |

### 7.3 核心算法与数据结构

- **Top-K 美食推荐**：最小堆维护前 K 条，O(n log K)；菜系过滤先缩小候选集再执行 Top-K，进一步降低计算量。
- **模糊查询**：子串匹配（KMP 或 Boyer-Moore）处理名称包含关系；Trie 前缀树支持店名/菜系前缀联想；可扩展编辑距离处理拼写错误。
- **距离排序**：调用成员 A 图上最短路径接口获取真实距离，禁止直线距离。

### 7.4 Q&A

**Q：美食推荐与旅游推荐的 Top-K 实现可以复用吗？**  
A：可以。成员 B 将 Top-K 封装为通用模块，传入不同的排序字段配置（`heat`/`rating`/`distance`）即可复用于景点推荐、美食推荐和日记推荐，减少重复代码。
