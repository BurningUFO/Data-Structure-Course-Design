# 项目代码骨架与成员职责划分 (修订版 - 分层架构)

## 1. 项目整体骨架 (src)
(目录结构保持不变，但增加对分层数据的支持说明)
- `data/sites/`：存放各景区的分层 JSON 数据。
- `src/graph/`：支持递归加载和层级检索。

---

## 2. 成员进度配合与依赖关系 (同步更新)
*   **成员 A 与 C**：成员 A 的 `loader.py` 现在需要递归读取 `data/sites/` 下的子文件夹。成员 C 需确保 `sub_graph_id` 与文件名一致。
*   **成员 A 与 B**：成员 B 的推荐逻辑现在需要区分“室内推荐”和“全景区推荐”。

---

## 3. 核心接口约定 (重要变更)

### 3.1 成员 B ← 成员 A：分层路径查询接口
由于引入了分层结构，路径查询现在支持跨层级搜索。

**接口名**：`query_routing(site_id, start_node_id, target_node_id, strategy='shortest_distance')`

**请求参数**：
- `site_id`: 所属景区 ID（如 `PKU`）。
- `start_node_id`: 起点 ID（可能在室内或室外）。
- `target_node_id`: 终点 ID。

**响应结构**：
```json
{
  "success": true,
  "segments": [
    {
      "layer": "indoor_LIB",
      "path": ["room_101", "gate_east"],
      "distance": 50
    },
    {
      "layer": "outdoor",
      "path": ["gate_east", "main_road_1"],
      "distance": 200
    }
  ],
  "total_distance": 250,
  "estimated_time": 180
}
```

---

## 4. 协作守则 (修订)
1.  **节点 ID 全局唯一**：成员 C 必须保证不同层级间的节点 ID 不重复。
2.  **门节点 (Gate) 映射**：当一个节点被标记为 `is_gate` 时，它必须在 `outdoor.json` 和对应的 `indoor_XXX.json` 中同时存在，作为层级间的“锚点”。
3.  **按需加载**：成员 A 负责实现懒加载机制，仅在进入特定景区或建筑时加载对应的子图数据。
