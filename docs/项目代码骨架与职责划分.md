# 项目代码骨架与成员职责划分

## 1. 项目整体骨架 (src)

为了实现模块化开发并减少接口冲突，本项目采用统一的 `src/` 目录结构。所有核心业务逻辑必须存放在对应的子目录下。

```text
C:\code\Data-Structure-Course-Design\
├── src/                    # 核心代码公共区
│   ├── graph/              # 图数据结构维护
│   ├── routing/            # 路径规划核心算法
│   ├── search/             # 查询逻辑（精确、模糊、过滤）
│   ├── recommend/          # 排序与 Top-N 推荐算法
│   ├── diary/              # 旅游日记业务逻辑
│   ├── compress/           # 全文检索与数据压缩
│   ├── integration/        # 模块联调与适配层
│   └── main.py             # 系统启动入口
├── data/                   # 公共数据集 (JSON/CSV)
├── tests/                  # 自动化测试用例
├── docs/                   # 项目文档与周报
└── memberA/B/C/            # 个人私有区（仅放笔记/草稿）
```

---

## 2. 成员进度配合与依赖关系

经过对成员 A、B、C 计划的审查，三方的进度安排高度互补且无冲突：

*   **数据依赖**：成员 C 在第 6 周产出基础数据集，解决 A（建图）和 B（推荐）的“无米之炊”问题。
*   **接口依赖**：成员 A 在第 7 周交付距离接口，使成员 B 能够完成“按距离排序”的功能。
*   **集成依赖**：成员 B 在第 11-12 周接收成员 C 的全文检索结果，完成日记模块的深度集成。
*   **最终合力**：成员 C 作为大总管，负责在第 13-15 周将各模块通过 `main.py` 串联并进行压力测试。

---

## 3. 成员权限与文件夹职责

所有成员拥有仓库的 Read/Write 权限，但为了保证代码稳定性，请严格遵守以下**目录所有权**原则：

| 负责成员 | 核心文件夹 | 职责说明 | 提交限制 |
| :--- | :--- | :--- | :--- |
| **成员 A** | `src/graph/`, `src/routing/` | 负责图建模、Dijkstra、TSP 多目标路径规划及距离接口。 | 拥有该目录的最终决定权，修改接口需通知成员 B。 |
| **成员 B** | `src/search/`, `src/recommend/`, `src/diary/` | 负责查询、Top-N 排序、推荐算法及日记业务逻辑。 | 调用 A 的接口，若需修改 `routing` 逻辑需联系 A。 |
| **成员 C** | `data/`, `src/compress/`, `tests/`, `src/integration/` | 负责原始数据、全文检索、压缩算法、集成测试及文档汇总。 | 拥有数据格式的定义权；负责合并 A 和 B 的代码分支。 |

### 提交规范 (Commit Message Convention)
*   成员 A: `feat(routing): implement dijkstra algorithm`
*   成员 B: `feat(search): add fuzzy search for scenic spots`
*   成员 C: `data: update scenic_spots.json` | `test: add integration test cases`

---

## 4. 协作守则
1.  **不修改他人目录**：除非经过对方同意，严禁直接修改非自己负责的文件夹。
2.  **接口先行**：在写代码前，先在 `docs/api.md` 中定义好输入输出。
3.  **不提交 `main` 分支**：建议每个人在自己的分支（如 `feat/member-a`）开发，由成员 C 定期进行合并。
