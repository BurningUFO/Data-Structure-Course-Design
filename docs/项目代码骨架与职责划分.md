# 项目代码骨架与成员职责划分（第八周联调修订版）

## 1. 项目整体骨架
- `data/global_sites.json`：全局景区注册表，定义 `site_id` 与子图清单。
- `data/sites/{site_id}/`：标准分层图数据目录，当前已支持直接加载 `outdoor.json`、`indoor_*.json`。
- `src/graph/`：图结构与标准数据 loader。
- `src/routing/`：单目标、多目标、交通方式过滤与跨层路径规划。
- `src/search/`、`src/recommend/`：成员 B 的查询、排序、推荐与业务服务层。

---

## 2. 成员进度配合与依赖关系
- **成员 A 与 C**：成员 A 现在原生支持读取 `data/sites/{site_id}/*.json`；成员 C 需继续保证 `global_sites.json` 中的 `sub_graphs` 与实际文件一致，且节点 `id` 全局唯一。
- **成员 A 与 B**：成员 A 的 `query_distance` / `query_routing` 已统一支持可选 `site_id`，并明确 `shortest_time` 的返回单位为秒；成员 B 可继续通过适配层调用，不需要改业务层入参顺序。
- **成员 B 与 C**：标准分层数据已可直接作为默认查询数据源；旧 `data/成员Cdata/scenic_spots.json` 仅保留历史兼容用途，如继续使用必须补 `node_id` 或 `map_node_id`。
- **成员 B 与 C（第十周新增）**：日记全文检索业务层统一消费最小字段集 `diary_id`、`title`、`matched_terms`、`score`、`destination`、`destination_node_id`；成员 B 对外统一封装为 `query_type="diary_fulltext_search"`，并保持 `results` / `data` 双字段兼容。

---

## 3. 核心接口约定

### 3.1 `site_id` 含义
- `site_id` 表示景区/校园站点标识，对应 `global_sites.json` 中 `sites[].id`。
- 标准数据目录约定为 `data/sites/{site_id}/`，例如 `PKU` 对应 `data/sites/PKU/`。
- 在成员 A 的接口中，`site_id` 现在是**可选参数**：
  - 不传时，默认使用当前图对象绑定的景区。
  - 传入时，会校验是否与当前图对象一致；不一致则返回失败信息。

### 3.2 成员 B ← 成员 A：单目标路径接口

**完整路径接口**

```python
query_routing(
    start_node_id,
    target_node_id,
    strategy="shortest_distance",
    transport_mode=None,
    site_id=None,
)
```

**轻量距离接口**

```python
query_distance(
    start_node_id,
    target_node_id,
    strategy="shortest_distance",
    transport_mode=None,
    site_id=None,
)
```

**请求参数**
- `start_node_id`：起点节点 ID。
- `target_node_id`：终点节点 ID。
- `strategy`：`shortest_distance` 或 `shortest_time`。
- `transport_mode`：交通方式过滤，可选。
- `site_id`：景区 ID，可选。

**返回语义**
- `shortest_distance`：权重单位为米。
- `shortest_time`：权重单位为秒。
- `query_routing(...)` 会同时返回显式距离和显式时间字段。
- `query_distance(...)` 只返回单个标量：
  - `shortest_distance` 返回米。
  - `shortest_time` 返回秒。

### 3.3 成员 B ← 成员 A：多目标路径接口

```python
query_multi_target(
    start_node_id,
    target_node_ids,
    strategy="shortest_distance",
    transport_mode=None,
    return_to_start=True,
    site_id=None,
)
```

**当前能力**
- 基于点对点最短路 + 状态压缩 DP 计算访问顺序。
- 支持最多 12 个目标点。
- 返回完整访问顺序、拼接后的总路径、总权重、总距离、总时间，以及各段 `leg_results`。

### 3.4 成员 B ← 成员 C：日记全文检索最小字段契约

成员 C 的全文检索实现可以是独立函数、索引对象或离线脚本包装，但接入成员 B 业务层时，至少应提供以下结果字段：

```json
{
  "diary_id": "diary_003",
  "title": "图书馆自习攻略",
  "matched_terms": ["图书馆", "自习"],
  "score": 42.0,
  "destination": "北京大学",
  "destination_node_id": "library"
}
```

业务层约束：
- 成员 B 对外统一返回 `query_type="diary_fulltext_search"`。
- `results[*].id` 与 `results[*].diary_id` 保持相同值，便于沿用现有日记卡片与测试断言。
- `results[*].snippet` 可由成员 B 侧补齐，不要求 C 侧必须生成。
- 若 C 侧检索实现暂未合入，成员 B 可先使用标题 / 正文 / 标签的最小回退检索，但不得改变上述字段口径。

## 4. 协作守则
1. **节点 ID 全局唯一**：成员 C 必须保证不同层级间的节点 ID 不重复。
2. **门节点映射一致**：室外建筑门节点通过 `sub_graph_id` 指向对应室内图；室内图入口节点需标记 `is_gate=true`。
3. **标准分层数据优先**：新开发默认以 `data/sites/{site_id}/` 为准；旧 `map_nodes.json`、`map_edges.json`、`成员Cdata/scenic_spots.json` 仅保留历史兼容用途。
4. **接口变更先改文档**：若后续继续调整路径接口字段或命名，必须先同步本文件与 `docs/数据字典.md`。
